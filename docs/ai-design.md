# 媒体系统「AI 智能入库」产品设计说明

> 本文档回答 AI 产品面试中高频的几个问题：数据为什么这么清洗切分、模型为什么选这个、
> 效果怎么评估、Token 成本怎么降、异常怎么兜底、Bad Case 怎么收集、为什么不用 Agent、
> 以及如何形成产品迭代闭环。每一个决策都对应代码里的具体实现。

## 一、产品定位与核心价值

**用户痛点**：素材库运营最耗时的一步是「给素材打标签、写标题、归分类」。一张图要手动想标题、写描述、挑 5~8 个标签、选分类，一张约 30~60 秒，批量入库时成本极高。

**AI 的价值**：不是「全自动」，而是「建议 + 回填」。AI 看图生成标题/描述/标签/分类并回填到表单，用户一眼扫过、微调后确认。这样既省了 80% 的手动工作，又保留人工最终决策权——因为打错标签会污染后续搜索和推荐，必须人工兜底。

**核心使用链路**：
```
上传图片 → 点「AI 智能识别」→ 图片压缩 → glm-4v-flash 看图
        → 解析 JSON → 分类名规则映射到分类树 → 回填表单（可改）
        → 确认入库 → 记录 bad case（采纳/修改）
```

## 二、七个维度逐一回答

### 1. 数据：为什么这么清洗、切分

**没有用 RAG/向量库**，而是用「受控分类字典 + few-shot 约束」：

- 素材分类是**有限的受控集合**（`media_category` 表里的分类树）。RAG 是为开放域长文本检索设计的，这里答案空间本来就小，用 RAG 反而引入「检索不准 → 生成跑偏」的风险。
- 做法：把分类树清洗成一个**可枚举清单**（逗号连接，`AiAnalyzeService` 里 `categoryService.list()` → 拼接），直接写进 prompt，逼模型在受控集合里选，而不是自由发挥。
- 图片在喂给模型前**压缩到最长边 768**（`AiAnalyzeService.compress()`）：既降低 token，又抹掉与原图无关的高频细节，视觉模型对缩略图打标签足够。

### 2. 模型：为什么选这个

选 **`glm-4v-flash`**（智谱视觉模型），理由：

1. **免费**：BigModel 平台永久免费，课程项目/学生可用，无成本门槛。
2. **国内直连**：无需代理，部署环境稳定（对比 OpenAI 国内不可达）。
3. **视觉 + 快**：`flash` 是轻量档，打标签这种「看图说短句」任务不需要旗舰模型，速度快、成本低。

模型名做成**可配置**（`ai.zhipu.vision-model`），将来想换 `glm-4v-plus` 或别的模型，只改配置不改代码。

### 3. 效果怎么评估

- **离线**：准备 50 张已人工标注的图片，跑一遍 AI，算分类准确率、标题/标签的主观打分（1~5 分）。
- **上线（核心北极星指标）＝ 采纳率**：`采纳率 = 未修改 AI 建议的入库次数 / 用了 AI 的入库总次数`。这是比「准确率」更接近商业价值的指标——用户没改，说明 AI 省了事；用户改了，说明 AI 没答到点子上。
- 数据来源就是 `ai_bad_case` 表，`adopted` 字段直接可聚合出采纳率。

### 4. 交互：用户为什么需要 AI

见「产品定位」。关键设计：**AI 只做「建议 + 回填」，绝不自动入库**。原因：打错标签会污染搜索/推荐，人工确认是质量的最后一道闸门。所以交互上 AI 结果全部落在可编辑表单里，用户确认后才入库。

### 5. 工程：Token 成本怎么降、异常怎么兜底

**降成本**（`ZhipuAiClient` + `AiAnalyzeService`）：
- 图片压缩到最长边 768（视觉 token 与像素面积正相关）。
- `max_tokens` 上限 512（标题+描述+标签是短文本，512 足够）。
- `temperature = 0.3`，输出更稳定，减少重试。

**异常兜底**（关键：AI 失败不拖垮入库主流程）：
- `ZhipuAiClient` 设 15s 超时，超时/HTTP 非 200 直接抛异常。
- `AiAnalyzeService.analyze()` 用 try-catch 兜底，任何失败返回 `fallback=true` + 提示语。
- 前端收到 `fallback=true` 时提示「请手动填写」，表单照常可用——**AI 是加分项，不是必经节点**。
- 未配置 API Key（占位符）时 `isConfigured()` 返回 false，直接走降级，不发起请求。

### 6. 运营：Bad Case 怎么收集、怎么持续优化

- **收集**：用户每用一次 AI 后入库，前端把「AI 原始输出 vs 用户最终值」成对写入 `ai_bad_case` 表（含 `adopted` 采纳标记）。
- **复盘**：每周看三件事——① 采纳率趋势；② 被改得最多的分类/标签（说明模型在这些类目上表现差）；③ 抽样看「AI 建议了什么、用户改成了什么」的差异，归纳成新的 few-shot 示例或 prompt 约束。
- **闭环**：`收集 → 归因 → 改 prompt/加示例 → 重新评估 → 上线`，采纳率就是这条闭环的仪表盘。

### 7. 规则 vs 模型、为什么不用 Agent、节点失败怎么办

**为什么不用 Agent**：打标签是**单步、确定性输入输出**，不需要工具调用、多轮规划、反思。上 Agent 只会增加延迟、成本和不可控，属于「杀鸡用牛刀」。

**什么时候规则、什么时候模型**：
- **模型**负责「看图理解 + 语言生成」（标题、描述、标签）——这是规则写不出来的。
- **规则**负责「分类映射」：模型返回分类名后，用**模糊匹配**（`matchCategory`）对齐到现有分类树；匹配不上就归「未分类」，由用户在表单里选。**分类必须是受控枚举，绝不让模型自由造分类**，否则分类树会失控。

**节点失败后如何保证任务继续**：AI 是「并行可选分支」，失败即降级为纯手动填写，上传主流程（文件保存 + 入库）完全不依赖 AI 结果，链路不会断。

## 三、落地位置速查

| 决策 | 代码 |
|---|---|
| 视觉模型调用 + 超时/降级 | `ai/ZhipuAiClient.java` |
| 图片压缩 + 解析 + 规则映射 | `ai/AiAnalyzeService.java` |
| 结果 DTO（含 fallback 标记） | `ai/AiTagResult.java` |
| 分析接口 | `MediaController#aiAnalyze` |
| bad case 落库接口 | `MediaController#recordAiBadCase` |
| bad case 表 | `sql/init.sql` 的 `ai_bad_case` |
| 前端回填 + 上报采纳信号 | `templates/media/upload.html` |
| 模型/超时/Token 配置 | `application.yml` 的 `ai.zhipu` |
